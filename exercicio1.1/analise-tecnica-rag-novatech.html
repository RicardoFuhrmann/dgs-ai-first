📊 PDFs com Tabelas Complexas (15+ colunas)

Desafio

Parsers PDF padrão (PyMuPDF, pdfplumber) extraem texto linha a linha, destruindo a relação coluna → valor. Uma tabela de frete com 15 colunas e 80 linhas (=1.200 células) se torna uma sequência de tokens sem semântica posicional. Células mescladas e cabeçalhos multlinha ampliam o problema.

Impacto na qualidade

  • A pergunta "frete para cliente Tipo B, Região Sudeste, carga > 500 kg" exige cruzar três dimensões; sem estrutura tabular o modelo não consegue navegar corretamente.
  • Risco de alucinação: o LLM "inventa" um valor plausível quando os dados estão embaralhados.
  • Retrieval prejudicado: embeddings de texto desestruturado têm baixa precisão semântica para perguntas numéricas.

Estratégia de tratamento

  • Parser especializado: pdfplumber com extração por bbox ou Camelot para tabelas com linhas; Azure Document Intelligence (Form Recognizer) para tabelas complexas/mistas — acurácia de 90–95% em tabelas bem formatadas.
  • Conversão para Markdown: cada tabela vira um bloco | col1 | col2 | … | antes de ser chunkeada; o LLM interpreta Markdown tabular nativamente.
  • Chunk por tabela inteira: não quebrar tabelas no meio; manter cada tabela como um único chunk (mesmo que ultrapasse 500 tokens — ver Bloco 4).
  • Metadados enriquecidos: tag tipo=tabela_frete, num_colunas=15, pagina=3 para filtrar antes do retrieval.
🔍 PDFs Escaneados (OCR necessário)

Desafio

Documentos escaneados são imagens; não há texto extraível. O pipeline padrão de PDF → texto retorna vazio ou ruído. Qualidade da digitalização (DPI, inclinação, manchas) varia enormemente, afetando a acurácia do OCR. Estima-se que, sem tratamento, 20–40% do conteúdo desses documentos fique inacessível ao retrieval.

Impacto na qualidade

  • Documentos inteiros ausentes do índice vetorial — o assistente responde "não encontrei informações" para conteúdo que existe.
  • OCR com baixa qualidade introduz tokens corrompidos ("frefe" por "frete"), degradando embeddings e retrieval.
  • Fluxogramas/imagens incorporadas permanecem opacos mesmo com OCR textual.

Estratégia de tratamento

  • Pipeline OCR dedicado: Azure AI Document Intelligence (melhor para documentos corporativos) ou Google Document AI; acurácia >98% em documentos limpos, 85–92% em escaneados comuns.
  • Pré-processamento de imagem: deskew + denoising com OpenCV antes do OCR para documentos de baixa qualidade.
  • Confiança mínima: definir threshold de confiança OCR (ex.: ≥ 0,80); chunks abaixo desse limiar recebem flag ocr_quality=low e são tratados com cuidado extra no prompt.
  • Fluxogramas: usar Vision API (GPT-4o com visão ou Azure AI Vision) para descrever a imagem em texto antes de indexar.
  • Revisão humana: listar documentos com confiança baixa para revisão periódica pela equipe de gestão documental.
📚 Wiki Confluence (links internos + macros)

Desafio

Uma página Confluence pode ser um sumário que referencia 10 sub-páginas via links internos. As macros customizadas (ex.: jira-issues, expand, status) são renderizadas dinamicamente — o HTML bruto exportado contém tags proprietárias sem conteúdo textual. Se cada página for ingerida isoladamente, o contexto fica fragmentado.

Impacto na qualidade

  • Pergunta "qual o procedimento completo de reclamação?" retorna apenas o trecho da página-pai, ignorando os detalhes nas páginas-filhas.
  • Macros não renderizadas geram lixo textual que polui embeddings.
  • Links internos quebram após exportação, impossibilitando rastreamento de fonte.

Estratégia de tratamento

  • API Confluence: usar a API REST v2 para extrair conteúdo renderizado (campo body.storage + body.view), não o HTML bruto, garantindo que macros sejam resolvidas.
  • Grafo de páginas: ao ingerir, rastrear parent_id e child_pages; incluir contexto da página-pai no metadata de cada chunk filho (parent_title, parent_url).
  • Stripping de macros: pipeline de limpeza com regex + BeautifulSoup para remover tags Confluence (ex.: <ac:structured-macro>) preservando apenas conteúdo semântico.
  • Chunking hierárquico: dividir por seção H2/H3, mantendo título da página como cabeçalho de cada chunk para preservar contexto.
  • Webhook de atualização: Confluence permite webhooks em alterações de página — usar para re-ingestão incremental em vez de re-ingerir tudo mensalmente.
📋 Planilhas Excel (fórmulas interdependentes)

Desafio

O RAG trabalha com texto; fórmulas Excel (=VLOOKUP(A2, TabelaFrete!$A:$F, 3, FALSE)) são procedimentos computacionais, não dados. Ao exportar para texto/CSV, a fórmula aparece literalmente — sem o valor calculado. Em planilhas com 50 abas e fórmulas interdependentes, o valor de uma célula pode depender de 5 outras abas.

Impacto na qualidade

  • O LLM não consegue executar fórmulas; responde com o texto da fórmula em vez do resultado — completamente inútil para o usuário.
  • Perda dimensional: uma tabela 2D (linhas × colunas) vira uma sequência linear, perdendo a relação cruzada essencial para cálculos de frete.
  • Desatualização: planilhas atualizadas mensalmente sem re-ingestão automática geram respostas baseadas em dados obsoletos.

Estratégia de tratamento

  • Exportar valores, não fórmulas: usar openpyxl com data_only=True ou xlwings (que abre o Excel e lê valores calculados) para capturar resultados reais.
  • Conversão a Markdown tabular: cada aba relevante vira uma tabela Markdown; incluir cabeçalhos de linha e coluna explícitos ("Tipo de Cliente | Região | Peso (kg) | Frete (R$)").
  • Separação de abas por domínio: não fundir todas as abas em um único documento; cada aba = um documento independente com metadata (aba=TabelaFreteNacional, atualizado=2026-05).
  • Tabelas de referência como contexto fixo: planilhas pequenas o suficiente (<2.000 tokens) podem ser injetadas diretamente no system prompt como "dados de referência", eliminando a necessidade de retrieval.
  • Pipeline de re-ingestão mensal: integrar ao SharePoint via Microsoft Graph API para detectar versões novas e re-processar automaticamente.

3.2 — O fenômeno Lost in the Middle

Pesquisas publicadas (Liu et al., 2023 — "Lost in the Middle: How Language Models Use Long Contexts") demonstram que LLMs como GPT-4o têm desempenho de atenção não uniforme ao longo do contexto:

  • Posições inicial e final do contexto recebem maior atenção — o modelo se lembra bem do que está no início e no fim do prompt.
  • Posições intermediárias sofrem queda severa de atenção — informação crítica no meio de um contexto longo é frequentemente ignorada, mesmo que seja exatamente o que responde à pergunta.
  • O efeito é agravado com o aumento do número de documentos: com 20+ chunks, a precisão de recuperação de informação do modelo cai significativamente.

Implicações práticas para a NovaTech:

Nº de chunks enviados Comportamento esperado do GPT-4o Risco
3 – 5 chunks Atenção uniforme; alta precisão na resposta Baixo
6 – 10 chunks Leve degradação em chunks intermediários Médio
11 – 20 chunks Chunks do meio frequentemente ignorados; respostas incompletas Alto
20+ chunks Resposta baseia-se apenas nos primeiros e últimos chunks; resto perdido Crítico

Para uma pergunta como "Como calcular o frete para envio com seguro?", se o chunk com a fórmula correta estiver na posição 12 de 20, o modelo provavelmente irá ignorá-lo e fabricar uma resposta baseada nos chunks que viu melhor — gerando alucinação com aparência de confiança.

3.3 — Impacto na Estratégia de Retrieval: qual o número ideal de chunks?

✅ Recomendação: enviar entre 5 e 8 chunks por query

Este range equilibra cobertura de informação (evitar que o chunk correto não seja recuperado) com qualidade de atenção do modelo (evitar lost in the middle).

Por que não enviar o máximo possível?

  • Efeito lost in the middle: mais chunks = mais probabilidade de a informação relevante ficar no meio do contexto e ser ignorada.
  • Ruído semântico: chunks marginalmente relevantes introduzem informação contraditória ou redundante, confundindo o modelo na síntese.
  • Custo proporcional: GPT-4o cobra por token de entrada; 245 chunks = ~122.500 tokens/query. A 320 queries/dia com 60% de consulta documental = ~192 queries × 122.500 tokens = ~23,5M tokens de entrada/dia — custo potencialmente proibitivo.
  • Latência: processar 122K tokens leva mais tempo, aumentando o tempo de resposta percebido pelos atendentes.

Estratégia de retrieval complementar ao limite de chunks:

  • Re-ranking: recuperar 20–30 candidatos via busca vetorial (recall alto) e usar um modelo de re-ranking cross-encoder (ex.: ms-marco-MiniLM) para selecionar os top 5–8 com maior relevância contextual.
  • Posicionamento estratégico: colocar o chunk com maior score de relevância primeiro no contexto (não no meio), explorando o viés de atenção inicial a favor do sistema.
  • Busca híbrida: combinar busca vetorial (semântica) com BM25 (léxica) — especialmente importante para termos técnicos precisos como códigos de produto ou nomes de regiões.

Bloco 4

Recomendação de Estratégia de Chunking

4.1 — Tamanho ideal de chunk

As perguntas do usuário são factuais e específicas (prazo para região X, política para produto Z, procedimento para situação W). Não são perguntas de síntese que requerem 10 páginas de contexto — requerem o parágrafo ou a linha de tabela certa.

Tamanho recomendado: 300 – 500 tokens por chunk
  • 300 tokens: para tabelas e planilhas (preservar linhas completas; evitar excesso de ruído)
  • 400–500 tokens: para texto narrativo (PDFs e wiki) — captura um parágrafo completo + contexto imediato
  • Exceção: tabelas inteiras que ultrapassem 500 tokens devem ser mantidas como chunk único (até 1.000 tokens), priorizando integridade estrutural sobre tamanho uniforme

Justificativa pelo tipo de pergunta:

  • Chunks muito pequenos (<150 tokens): perdem contexto da frase/parágrafo — a resposta não tem informação suficiente para ser precisa.
  • Chunks muito grandes (>800 tokens): aumentam ruído no contexto e reduzem a precisão do embedding (vetores representam "assuntos médios" em vez de "respostas específicas").
  • 300–500 tokens é o sweet spot empiricamente validado para QA sobre documentação operacional.

4.2 — Overlap entre chunks

Overlap recomendado: 10–15% do tamanho do chunk Para chunks de 400 tokens → overlap de 40–60 tokens (3–4 frases).

Por quê overlap é necessário:

  • Uma informação-chave frequentemente aparece na fronteira entre dois chunks (ex.: uma regra que começa no parágrafo final do chunk N e conclui no parágrafo inicial do chunk N+1).
  • Sem overlap, essas informações nunca são recuperadas completas — o modelo vê fragmentos sem conclusão.
  • Com overlap de 50 tokens, ambos os chunks capturam a informação de fronteira, aumentando a probabilidade de ao menos um deles ser recuperado.
  • Overlap >20% não é recomendado: aumenta redundância no contexto (dois chunks quase idênticos competem por atenção) e eleva o número de chunks na base sem benefício proporcional.

4.4 — Mitigação do efeito Lost in the Middle

A estratégia de chunking combate lost in the middle em três frentes:

  1. Chunks menores e mais precisos (300–500 tokens): Ao manter chunks compactos, cada chunk carrega alta densidade semântica — um chunk de 400 tokens sobre "frete com seguro" contém quase somente essa informação, sem diluição. Isso eleva o score de relevância no retrieval, aumentando a chance de o chunk certo ser selecionado e posicionado no início do contexto.
  2. Limite rígido de 5–8 chunks por query (Bloco 3): Com poucos chunks no contexto, não há "meio profundo" — mesmo o chunk na posição 5 está suficientemente próximo do início e fim para receber atenção adequada.
  3. Re-ranking + posicionamento por relevância: O chunk com maior score de re-ranking é posicionado primeiro no contexto. Como a atenção inicial é mais forte, colocar a resposta mais provável logo no início maximiza a probabilidade de uso correto pelo modelo.

4.5 — Chunking fixo, semântico ou hierárquico?

Recomendação: abordagem híbrida — semântico para texto, hierárquico para wiki, fixo por unidade para tabelas
Abordagem Quando usar neste projeto Vantagem Limitação
Fixo
(N tokens com overlap)		 PDFs escaneados pós-OCR; planilhas simples Simples de implementar; previsível Pode cortar no meio de uma frase crítica
Semântico
(por parágrafo/sentença)		 PDFs narrativos (manuais, políticas) Preserva unidades de significado; melhor embedding Tamanho variável; mais complexo de implementar
Hierárquico
(seção → sub-seção → parágrafo)		 Wiki Confluence; PDFs com estrutura clara de headings Preserva contexto navegacional; suporta multi-hop Depende de estrutura documental consistente

Justificativa da híbrida: Não existe uma abordagem superior universal — o ganho vem de adequar o método à estrutura do documento. Um chunking semântico em uma planilha Excel não faz sentido (não há parágrafos). Um chunking fixo em uma wiki hierárquica desperdiça a estrutura que torna os documentos navegáveis.

Para implementação prática no projeto NovaTech, recomenda-se usar LangChain (com RecursiveCharacterTextSplitter para semântico, MarkdownHeaderTextSplitter para hierárquico) ou LlamaIndex (com HierarchicalNodeParser), que suportam todas as três abordagens com configuração por tipo de documento.

Síntese Final

Principais Riscos Técnicos e Mitigações

A análise revela uma base documental tecnicamente heterogênea (~4,7M tokens) com três riscos críticos que, se não tratados, comprometem a viabilidade do assistente mesmo com a melhor arquitetura de retrieval:

🔴 Risco 1 — Alta
Perda de estrutura em tabelas e planilhas

As perguntas mais críticas do atendimento (cálculos de frete, SLAs por região) dependem exatamente das fontes mais difíceis de ingerir corretamente: tabelas PDF e planilhas Excel.

Mitigação: Azure Document Intelligence para extração de tabelas + conversão para Markdown tabular + chunking por tabela inteira + exportação de valores calculados das planilhas (não fórmulas).

🔴 Risco 2 — Alta
Alucinação por retrieval impreciso + lost in the middle

Com 9.333 chunks na base, enviar chunks irrelevantes ou muitos chunks simultaneamente ao LLM gera respostas incorretas com aparência de confiança — especialmente perigoso em contexto de logística (valores errados de frete, prazos incorretos).

Mitigação: Retrieval em dois estágios (busca vetorial → re-ranking); limite de 5–8 chunks/query; posicionamento do chunk mais relevante no início do contexto.

🟡 Risco 3 — Média
Desatualização silenciosa da base

Documentação atualizada mensalmente por 3 áreas sem processo unificado pode gerar contradições entre versões. O assistente pode responder com base em dados desatualizados sem nenhum aviso ao usuário.

Mitigação: Metadata de data_ingestão e versão em todos os chunks; pipeline de re-ingestão incremental via Microsoft Graph API + webhooks Confluence; instrução no system prompt para citar data do documento na resposta.

Conclusão arquitetural

O projeto NovaTech é viável tecnicamente, mas seu sucesso depende criticamente do investimento na camada de ingestão (estimativa: 40–50% do esforço técnico total) — não no LLM em si. Um modelo menor com dados bem estruturados supera consistentemente um modelo melhor com dados mal ingeridos. A estratégia de chunking híbrida proposta, combinada com retrieval em dois estágios e metadados ricos por tipo de fonte, endereça os três riscos e cria a base para que o assistente atinja a meta de redução de 12 → 2 minutos por chamado.
