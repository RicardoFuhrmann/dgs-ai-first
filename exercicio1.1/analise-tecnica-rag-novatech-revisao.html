📊 PDFs com Tabelas Complexas (15+ colunas)

Desafio

Parsers PDF padrão (PyMuPDF, pdfplumber) extraem texto linha a linha, destruindo a relação coluna → valor. Uma tabela de frete com 15 colunas e 80 linhas (=1.200 células) se torna uma sequência de tokens sem semântica posicional. Células mescladas e cabeçalhos multilinha ampliam o problema. Tabelas sem bordas explícitas (muito comuns em PDFs exportados do Excel) chegam a 40–60% de perda estrutural com parsers padrão.

Impacto na qualidade

  • A pergunta "frete para cliente Tipo B, Região Sudeste, carga > 500 kg" exige cruzar três dimensões; sem estrutura tabular o modelo não consegue navegar corretamente.
  • Risco de alucinação: o LLM "inventa" um valor plausível quando os dados estão embaralhados.
  • Retrieval prejudicado: embeddings de texto desestruturado têm baixa precisão semântica para perguntas numéricas.

Estratégia de tratamento

  • Parser especializado: pdfplumber com extração por bbox somente para tabelas com bordas; Camelot (lattice mode) para tabelas com linhas; Azure Document Intelligence para tabelas complexas/mistas — acurácia de 75–90% em tabelas corporativas reais (não de marketing).
  • Detecção automática de tipo de tabela: testar extração por lattice e stream; comparar número de células detectadas; usar resultado com maior estrutura como validação cruzada.
  • Conversão para Markdown: cada tabela vira um bloco | col1 | col2 | … | antes de ser chunkeada; o LLM interpreta Markdown tabular nativamente.
  • Chunk por tabela inteira: não quebrar tabelas no meio; manter cada tabela como um único chunk (mesmo que ultrapasse 500 tokens — ver Bloco 4).
  • Metadados enriquecidos: tag tipo=tabela_frete, num_colunas=15, pagina=3, parser_usado, confianca_extracao para filtrar antes do retrieval.
  • Validação com golden samples: extrair manualmente 10–15 tabelas representativas; comparar com saída do parser; ajustar estratégia antes de processar os 800 PDFs.

Segurança / Acesso

Tabelas de frete podem conter valores contratuais sigilosos por cliente. Verificar se há documentos com restrição de acesso no SharePoint antes de ingerir — ver Bloco 6.

🔍 PDFs Escaneados (OCR necessário)

Desafio

Documentos escaneados são imagens; não há texto extraível. O pipeline padrão de PDF → texto retorna vazio ou ruído. Qualidade da digitalização (DPI, inclinação, manchas) varia enormemente, afetando a acurácia do OCR. Na prática, documentos corporativos brasileiros escaneados apresentam 65–85% de acurácia por página, não os 85–98% dos benchmarks de fornecedores — esses assumem documentos limpos em inglês.

Impacto na qualidade

  • Documentos inteiros ausentes do índice vetorial — o assistente responde "não encontrei informações" para conteúdo que existe.
  • OCR com baixa qualidade introduz tokens corrompidos ("frefe" por "frete"), degradando embeddings e retrieval.
  • Fluxogramas/imagens incorporadas permanecem opacos mesmo com OCR textual.
  • Efeito silencioso: o sistema parece funcionar, mas responde com lacunas desconhecidas — erros que não aparecem como erros óbvios.

Estratégia de tratamento

  • Pipeline OCR dedicado: Azure AI Document Intelligence ou Google Document AI; selecionar por amostragem em documentos reais da NovaTech antes de escolher.
  • Pré-processamento de imagem: deskew + denoising com OpenCV antes do OCR para documentos de baixa qualidade.
  • Confiança mínima por token: definir threshold ≥ 0,80; chunks abaixo recebem flag ocr_quality=low e são tratados com cuidado extra no prompt ("informação extraída de documento de baixa qualidade — confirme com a equipe").
  • Auditoria inicial obrigatória: antes de indexar, gerar relatório de confiança OCR por documento. Documentos com <70% de confiança média devem ser revisados manualmente ou re-escaneados antes da ingestão.
  • Fluxogramas: usar GPT-4o com visão para descrever a imagem em texto antes de indexar.
  • Revisão humana periódica: listar documentos com confiança baixa para revisão trimestral.
📚 Wiki Confluence (links internos + macros)

Desafio

Uma página Confluence pode ser um sumário que referencia 10 sub-páginas via links internos. As macros customizadas (ex.: jira-issues, expand, status) são renderizadas dinamicamente — o HTML bruto exportado contém tags proprietárias sem conteúdo textual. Se cada página for ingerida isoladamente, o contexto fica fragmentado. Em ambientes enterprise, a API REST do Confluence pode exigir aprovação de admin e ter rate limits baixos — fator operacional frequentemente ignorado.

Impacto na qualidade

  • Pergunta "qual o procedimento completo de reclamação?" retorna apenas o trecho da página-pai, ignorando os detalhes nas páginas-filhas.
  • Macros não renderizadas geram lixo textual que polui embeddings.
  • Links internos quebram após exportação, impossibilitando rastreamento de fonte.

Estratégia de tratamento

  • API Confluence REST v2: extrair conteúdo renderizado (campo body.storage + body.view), não o HTML bruto.
  • Grafo de páginas: ao ingerir, rastrear parent_id e child_pages; incluir contexto da página-pai no metadata de cada chunk filho (parent_title, parent_url).
  • GraphRAG para hierarquia profunda: para espaços Confluence com hierarquia de 3+ níveis, considerar abordagem de knowledge graph (Microsoft GraphRAG) para navegação multi-hop entre páginas relacionadas — especialmente eficaz para "qual o processo completo de X?" que atravessa múltiplas páginas.
  • Stripping de macros: pipeline de limpeza com regex + BeautifulSoup para remover tags Confluence.
  • Chunking hierárquico: dividir por seção H2/H3, mantendo breadcrumb no início de cada chunk ("Procedimentos > Reclamações > Carga Danificada").
  • Webhook de atualização: usar para re-ingestão incremental; validar com admin de TI que webhooks estão liberados no ambiente enterprise da NovaTech antes de incluir no plano.

Segurança / Acesso

Espaços Confluence têm permissões granulares. Ingerir um espaço inteiro pode trazer conteúdo restrito a determinados grupos. Mapear permissões antes da ingestão — ver Bloco 6.

📋 Planilhas Excel (fórmulas interdependentes)

Desafio

O RAG trabalha com texto; fórmulas Excel (=VLOOKUP(A2, TabelaFrete!$A:$F, 3, FALSE)) são procedimentos computacionais, não dados. Ao exportar para texto/CSV, a fórmula aparece literalmente — sem o valor calculado. Em planilhas com 50 abas e fórmulas interdependentes, o valor de uma célula pode depender de 5 outras abas. Usar openpyxl data_only=True só funciona se o arquivo foi salvo com valores calculados — planilhas abertas e modificadas mas não salvas corretamente no Excel retornam None em vez do valor.

Impacto na qualidade

  • O LLM não consegue executar fórmulas; responde com o texto da fórmula em vez do resultado — completamente inútil para o usuário.
  • Perda dimensional: uma tabela 2D (linhas × colunas) vira uma sequência linear, perdendo a relação cruzada essencial para cálculos de frete.
  • Desatualização: planilhas atualizadas mensalmente sem re-ingestão automática geram respostas baseadas em dados obsoletos.

Estratégia de tratamento

  • Exportar valores, não fórmulas: xlwings (abre o Excel real e lê valores calculados) é mais confiável que openpyxl data_only=True — este falha em planilhas não recalculadas antes do último save.
  • Validação de valores: comparar saída do parser com células-amostra verificadas manualmente; alertar se % de células None > 5%.
  • Conversão a Markdown tabular: cada aba relevante vira uma tabela Markdown com cabeçalhos de linha e coluna explícitos.
  • Separação de abas por domínio: cada aba = um documento independente com metadata (aba=TabelaFreteNacional, atualizado=2026-05, versao=3.2).
  • Tabelas de referência pequenas como contexto fixo: planilhas <2.000 tokens injetadas diretamente no system prompt eliminam retrieval para dados estáticos.
  • Pipeline de re-ingestão mensal: Microsoft Graph API para detectar versões novas no SharePoint e re-processar automaticamente — incluir notificação para equipe responsável confirmar que os dados foram atualizados corretamente.

3.2 — O fenômeno Lost in the Middle

🔄 Nota de revisão — Nuance sobre o estudo original

Liu et al. (2023) estudou modelos como GPT-3.5-turbo e Claude 2.1 — arquiteturas com limitações de atenção que o GPT-4o endereça parcialmente. Testes com GPT-4o mostram degradação menos severa no meio do contexto em relação aos modelos originais do estudo. Isso não elimina o fenômeno, mas significa que o limite de 5–8 chunks deve ser tratado como otimização de qualidade e custo, não como barreira técnica rígida. Para consultas analíticas complexas, 12–15 chunks cuidadosamente selecionados podem ser justificáveis.

Modelos LLMs de grande contexto têm desempenho de atenção não uniforme ao longo do contexto. O efeito é documentado e ainda relevante para GPT-4o, especialmente com contextos acima de 40K tokens:

  • Posições inicial e final do contexto recebem maior atenção — o modelo se lembra bem do que está no início e no fim do prompt.
  • Posições intermediárias sofrem queda de atenção em contextos longos — mais relevante acima de 20 chunks ou 10K+ tokens de retrieval.
  • Com GPT-4o, o ponto crítico parece estar em torno de 15–20 documentos (não 10–15 como nas pesquisas de 2023 com modelos anteriores).
Nº de chunks enviados Comportamento esperado do GPT-4o Risco
3 – 5 chunks Atenção uniforme; alta precisão na resposta Baixo
6 – 10 chunks Leve degradação em chunks intermediários; aceitável Baixo-Médio
11 – 20 chunks Chunks do meio sujeitos a menor atenção; custo cresce proporcionalmente Médio
20+ chunks Degradação significativa; custo alto; latência aumentada Alto

3.3 — Número ideal de chunks e adaptação por tipo de query

✅ Recomendação: janela adaptativa de 5–12 chunks por query

Queries simples/factuais → 5–8 chunks. Queries analíticas/comparativas → até 12 chunks com re-ranking rigoroso. O limite não deve ser fixo no código — deve ser parâmetro configurável por tipo de intent detectado na query.

Estratégia de retrieval em dois estágios:

  • Estágio 1 — Recall: recuperar 30–50 candidatos via busca híbrida (vetorial + BM25). Alta revocação, baixa precisão.
  • Estágio 2 — Precision: re-ranker cross-encoder seleciona top 5–12 com maior relevância contextual.
  • Re-ranker recomendado: cross-encoder/ms-marco-MiniLM-L-6-v2 para latência baixa (~80ms/query) ou cross-encoder/ms-marco-MiniLM-L-12-v2 para maior acurácia (~150ms). Para domínio logístico em português, avaliar fine-tuning com exemplos de queries reais após 2–3 semanas de uso.
  • Busca híbrida: combinar vetorial (semântica, peso ~0.7) com BM25 (léxica, peso ~0.3); pesos ajustáveis via calibração em golden dataset. Ferramentas: Elasticsearch (BM25 nativo), Weaviate (hybrid search nativo), Qdrant (sparse + dense vectors).
  • Posicionamento estratégico: chunk com maior score de re-ranking posicionado primeiro no contexto.

3.5 — Gerenciamento de histórico multi-turn

Conversas longas com atendentes acumulam histórico rapidamente. Estratégias para controlar crescimento:

  • Sliding window: manter apenas as últimas N mensagens; simples mas perde contexto de início de conversa.
  • Summarization progressiva: ao atingir 3.000 tokens de histórico, sumarizar as mensagens mais antigas em 300–500 tokens e continuar. GPT-4o-mini é custo-eficiente para sumarização.
  • Message importance scoring: preservar mensagens com informações críticas confirmadas (ex.: "cliente confirmou CEP 04567-890") e comprimir smalltalk.
  • Recomendação para NovaTech: sliding window de 8 turnos com sumarização das mensagens anteriores — cobre a maioria dos atendimentos (média de atendimento: 5–10 turnos).

Bloco 4

Recomendação de Estratégia de Chunking

4.1 — Tamanho ideal de chunk

As perguntas do usuário são factuais e específicas (prazo para região X, política para produto Z, procedimento para situação W). Não são perguntas de síntese que requerem 10 páginas de contexto — requerem o parágrafo ou a linha de tabela certa.

Tamanho recomendado: 300 – 500 tokens por chunk
  • 300 tokens: para tabelas e planilhas (preservar linhas completas; evitar excesso de ruído)
  • 400–500 tokens: para texto narrativo (PDFs e wiki) — captura um parágrafo completo + contexto imediato
  • Exceção: tabelas inteiras que ultrapassem 500 tokens devem ser mantidas como chunk único (até 1.000 tokens), priorizando integridade estrutural sobre tamanho uniforme
  • Nota: chunks menores melhoram a precisão do embedding (menos diluição semântica) mas aumentam o número total de chunks e o custo de re-ranking. Balancear conforme calibração no golden dataset.

4.2 — Overlap entre chunks

Overlap recomendado: 10–15% do tamanho do chunk Para chunks de 400 tokens → overlap de 40–60 tokens (3–4 frases).

4.4 — Mitigação do efeito Lost in the Middle

  1. Chunks menores e mais precisos (300–500 tokens): Alta densidade semântica por chunk → score de relevância mais alto no retrieval → mais chance do chunk certo ser selecionado e posicionado no início do contexto.
  2. Janela adaptativa de chunks por query (5–12): Para queries simples, 5–8 chunks eliminam a "zona de baixa atenção". Para queries analíticas, até 12 com re-ranking rigoroso.
  3. Re-ranking + posicionamento por relevância: Chunk com maior score de re-ranking posicionado primeiro no contexto. Estratégia de "sandwich": chunk mais relevante primeiro, segundo mais relevante por último, restantes no meio.

Avaliação de Qualidade do RAG

🆕 Seção ausente na v1 — crítica para validar e manter o sistema

Um sistema RAG sem framework de avaliação é um sistema cego: funciona (ou falha) sem que a equipe saiba em qual direção. A avaliação deve começar antes da produção (golden dataset) e continuar continuamente (monitoramento em produção).

5.1 — Métricas fundamentais do RAG (Framework RAGAS)

Faithfulness
A resposta é fiel ao conteúdo dos chunks recuperados? (sem alucinação)
Meta: > 0,85
Answer Relevancy
A resposta responde de fato à pergunta feita?
Meta: > 0,80
Context Precision
Dos chunks recuperados, quantos são realmente relevantes?
Meta: > 0,70
Context Recall

Meta: > 0,75

5.2 — Golden Dataset: pré-requisito para ir a produção

O golden dataset é um conjunto de perguntas com respostas corretas validadas manualmente pela equipe de negócio da NovaTech. É o único mecanismo confiável para saber se o sistema funciona antes de expor a atendentes reais.

Especificação do Golden Dataset
  • Volume: 80–120 pares pergunta/resposta cobrindo os principais fluxos de atendimento (frete, SLAs, procedimentos, exceções)
  • Distribuição: ~40% perguntas sobre tabelas/planilhas; ~35% sobre procedimentos (wiki); ~25% sobre políticas (PDFs)
  • Tipos de pergunta: factuais simples, comparativas ("qual a diferença entre X e Y"), procedimentais ("como fazer X"), edge cases ("e se X não se aplicar?")
  • Responsável: equipe de negócio + gestão de atendimento — não a equipe de TI
  • Critério de aceitação para produção: Faithfulness > 0,85 e Answer Relevancy > 0,80 em todo o golden dataset

5.3 — Monitoramento contínuo em produção

O que registrar em cada query de produção:

  • Pergunta original (anonimizada/pseudonimizada conforme LGPD)
  • Chunks recuperados (IDs + scores de relevância)
  • Score do re-ranker para cada chunk
  • Resposta gerada
  • Feedback do usuário (thumbs up/down — ver 5.4)
  • Latência total e por etapa (retrieval, re-ranking, geração)

Alertas automáticos para:

  • Taxa de respostas "não encontrei informação" > 15% (possível gap de cobertura na ingestão)
  • Score médio de relevância dos chunks caindo >10% em relação à baseline (possível degradação do pipeline)
  • Latência p95 > 8 segundos por query
  • Taxa de feedback negativo > 20%

5.4 — Loop de feedback e melhoria contínua

  • Feedback inline: botão 👍/👎 ao final de cada resposta do assistente; opção de comentário livre para 👎.
  • Análise semanal: revisar todas as queries com feedback negativo; identificar padrões (tipo de fonte, tipo de pergunta, horário).
  • Ciclo de melhoria: chunks com baixo feedback → revisar ingestão da fonte → re-ingerir → re-testar no golden dataset → publicar nova versão.
  • Versionamento do índice: manter versão anterior do índice vetorial por 30 dias para rollback em caso de regressão.

Bloco 6 — Adicionado na Revisão v2

Segurança, LGPD e Conformidade

🆕 Seção ausente na v1 — requisito não-funcional crítico em ambiente corporativo

A documentação da NovaTech pode conter dados pessoais de clientes (em documentos de reclamação, histórico de entregas), valores contratuais sigilosos e informações operacionais sensíveis. A ingestão indiscriminada dessas fontes em um vector store cria riscos de conformidade que devem ser tratados antes do desenvolvimento.

6.1 — Mapeamento de dados sensíveis por fonte

Fonte Dados potencialmente sensíveis Risco LGPD Ação recomendada
PDFs (SharePoint) CPF/CNPJ de clientes em documentos de reclamação, valores contratuais individualizados Alto Classificar documentos por nível de sensibilidade antes de ingerir; mascarar PII com NER antes de gerar embedding
Wiki Confluence Procedimentos internos de precificação, informações de fornecedores, dados de funcionários Médio Mapear permissões de espaço/página na API; ingerir apenas conteúdo acessível ao perfil "atendente"
Planilhas Excel Valores de contrato por cliente, margens, acordos especiais Alto Identificar abas com dados contratuais individuais; não ingerir ou anonimizar antes da ingestão

6.2 — Controle de acesso no vector store

Um atendente de nível 1 não deve ter acesso via assistente a documentos restritos a gestores ou diretoria. Estratégias:

  • Metadados de permissão: adicionar campo nivel_acesso (ex.: publico, atendente, supervisor, restrito) em cada chunk durante a ingestão, baseado nas permissões do documento de origem.
  • Filtro obrigatório no retrieval: toda query deve incluir filtro nivel_acesso IN (perfis_do_usuario) antes da busca vetorial — não após. Buscar primeiro e filtrar depois expõe chunks indevidos ao ranking.
  • Auditoria de acesso: registrar qual usuário consultou quais chunks; relatório mensal para DPO (Data Protection Officer).

6.3 — Proteção de PII antes do embedding

  • Detecção de PII: usar NER (Named Entity Recognition) para identificar CPF, CNPJ, e-mail, telefone, endereço antes da ingestão. Bibliotecas: presidio-analyzer (Microsoft, open-source) ou spaCy com modelo treinado para português.
  • Mascaramento ou exclusão: substituir PII por tokens genéricos ("[CPF_CLIENTE]", "[EMAIL]") ou excluir o documento da base conforme política de dados.
  • Retenção: definir política de quanto tempo embeddings ficam no vector store; excluir chunks de documentos expirados ou revogados.

6.4 — Residência de dados e conformidade Azure

Dado que a NovaTech já usa Azure (SharePoint, Document Intelligence), a arquitetura deve priorizar serviços Azure Brazil South ou Azure East US 2 com data residency configurada para atender à LGPD (dados pessoais de cidadãos brasileiros). Evitar rodar embeddings ou armazenar chunks em regiões fora do escopo do acordo de processamento de dados com a Azure.

⚠️ Ação antes de iniciar o desenvolvimento Engajar o DPO (ou jurídico) da NovaTech para classificar as fontes documentais por nível de sensibilidade. Sem essa classificação, a ingestão pode criar passivo de conformidade que exige retrabalho completo na camada de acesso.

Síntese Final

Riscos Técnicos, Mitigações e Fases de Implementação

A análise revela uma base documental tecnicamente heterogênea (~4,7–5,5M tokens) com seis riscos que, se não tratados, comprometem a viabilidade ou a conformidade do assistente independentemente da qualidade do LLM escolhido.

🔴 Risco 1 — Alta
Perda de estrutura em tabelas e planilhas

As perguntas mais críticas do atendimento dependem das fontes mais difíceis de ingerir: tabelas PDF e planilhas Excel. Acurácia real de parsers em documentos corporativos é 15–30% abaixo dos valores de marketing.

Mitigação: Validar parsers com golden samples reais antes de escolher. Azure Document Intelligence + conversão Markdown + chunking por tabela + exportação de valores calculados (não fórmulas).

🔴 Risco 2 — Alta
Alucinação por retrieval impreciso

Com 9.300–11.000 chunks na base, enviar chunks irrelevantes ao LLM gera respostas incorretas com aparência de confiança — especialmente perigoso para valores de frete e prazos.

Mitigação: Retrieval em dois estágios (busca híbrida → re-ranking cross-encoder); janela adaptativa de 5–12 chunks; posicionamento do chunk mais relevante primeiro.

🔴 Risco 3 — Alta
Ausência de framework de avaliação

Ir a produção sem golden dataset e sem métricas RAGAS significa não saber se o sistema está funcionando ou falhando silenciosamente. Regressões serão detectadas por reclamações de usuários, não por alertas.

Mitigação: Golden dataset (80–120 pares) validado pela equipe de negócio antes do go-live. RAGAS em CI/CD. Monitoramento contínuo com alertas de degradação.

🟡 Risco 4 — Média
Segurança/LGPD e controle de acesso

Ingestão de documentos com PII ou dados contratuais sigilosos sem classificação prévia cria passivo de conformidade. Atendentes podem acessar via assistente conteúdo restrito a supervisores.

Mitigação: Classificação de documentos por nível de acesso antes da ingestão. Filtro obrigatório por perfil no retrieval. Mascaramento de PII com presidio-analyzer. Engajar DPO antes do desenvolvimento.

🟡 Risco 5 — Média
Desatualização silenciosa da base

Documentação atualizada mensalmente sem re-ingestão automática. Pior: após re-ingestão, chunks antigos e novos podem coexistir no índice gerando respostas contraditórias.

Mitigação: Metadata data_ingestão + versão em todos os chunks. Pipeline incremental via Graph API + webhooks. Invalidação de chunks ao re-ingerir documento — nunca apenas adicionar, sempre substituir.

🟡 Risco 6 — Média
Embedding drift e lock-in de modelo

Se o modelo de embedding for atualizado ou substituído, todos os ~10.000+ chunks precisam ser re-embedados para consistência. Sem planejamento, isso gera downtime ou inconsistências graves no retrieval.

Mitigação: Registrar modelo de embedding e versão em metadata de cada chunk. Planejar janela de re-ingestão completa semestral. Manter modelo de embedding fixo por ao menos 6 meses após lançamento. Avaliar custo de re-embedding antes de atualizar.

Fases de Implementação Recomendadas

O sucesso do projeto NovaTech depende da sequência correta: ingestão de qualidade primeiro, retrieval depois, interface por último. Ir rápido demais na interface antes de validar ingestão é o erro mais comum em projetos RAG.

  • Semana 1–2
    Fundação
    Classificação e auditoria documental Mapear níveis de acesso. Amostrar 20–30 documentos de cada tipo. Validar parsers e OCR com amostras reais. Definir critérios de qualidade mínima para ingestão. Engajar DPO.
  • Semana 3–5
    Ingestão
    Pipeline de ingestão e indexação Implementar parsers por tipo de fonte. Pipeline OCR com scoring de confiança. Conversão para Markdown. Chunking híbrido por tipo. Metadados enriquecidos. Mascaramento de PII. Vector store configurado com filtros de acesso.
  • Semana 6
    Baseline
    Golden dataset e métricas baseline Construir 80–120 pares Q/A com equipe de negócio. Rodar RAGAS. Estabelecer métricas baseline. Identificar gaps críticos antes de avançar.
  • Semana 7–9
    Retrieval
    Busca híbrida, re-ranking e orçamento de contexto Implementar retrieval em dois estágios. Calibrar pesos BM25/vetorial. Fine-tune de re-ranker (opcional). Testes de qualidade contra golden dataset. Atingir critérios de aceitação antes de avançar.
  • Semana 10–12
    Interface
    Interface, system prompt e rollout controlado Design do system prompt para o domínio logístico. Integração com sistema de atendimento. Rollout para 5–10% dos atendentes. Monitoramento de feedback. Ajuste iterativo.
Conclusão arquitetural revisada

O projeto NovaTech é viável tecnicamente, mas seu sucesso depende de três investimentos proporcionalmente corretos: (1) ingestão de qualidade — 40% do esforço; (2) retrieval preciso com avaliação contínua — 35%; (3) interface e system prompt — 25%. Um LLM melhor com dados mal ingeridos e sem métricas de avaliação não atinge a meta de 12→2 minutos por chamado — e não há como saber que está falhando até o dano ser perceptível pelos atendentes. A camada de avaliação (Bloco 5) e segurança (Bloco 6), ausentes na análise original, são co-requisitos do projeto, não opcionais.
